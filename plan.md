# Distributed Database Orchestration System for Postgres databases.

This system aims to transform traditional monolithic PostgreSQL deployments into distributed database systems using a Bring-Your-Own-Database (BYODB) approach. Users can attach multiple PostgreSQL instances to the platform, after which the orchestration system will manage sharding, replication, routing, and potentially shard key inference.

The system will operate directly on PostgreSQL syntax instead of introducing an internal query language in order to minimize query rewriting and avoid unnecessary syntax translation overhead. The platform will support pseudo-global transactions using a lightweight application-level two-phase commit (2PC) coordination strategy. Additionally, the system will include continuous monitoring, fault management, and observability capabilities while attempting to enforce practical ACID guarantees wherever feasible.

The architecture is intentionally optimized only for OLTP workloads and will not support OLAP-style queries. Since the system is shard-key dependent, all queries without shard keys (except controlled JOIN operations) will be rejected. Each PostgreSQL instance in the system will be referred to as a “Node”.

### Major Architectural Modules:

1. Metadata Module:  The Metadata Module is responsible for managing all node-related metadata within the orchestration system. This includes information such as node connection details, node role (primary or replica), node status, health information, and other operational metadata required for orchestration. Ideally, the metadata layer should be separated into multiple tables or collections to isolate connection configuration data from runtime operational metadata. This module acts as the central source of truth for the overall cluster topology.
2. Node manager: The Node Manager is responsible for maintaining the replication topology of a project. It allows the user to designate a node as a primary or replica, records the primary→replica relationships, and configures PostgreSQL native streaming replication between them.

4. Schema management service: The Schema Management Service is responsible for serial and non-concurrent schema ingestion across distributed nodes. Incoming DDL queries are executed sequentially to reduce the probability of schema divergence between nodes. The service uses lightweight application-level two-phase commit (2PC)-style coordination to minimize partial schema application failures across primary and replica nodes. In addition to schema synchronization, the module also maintains schema version history, migration metadata, rollback metadata, and schema audit logs for traceability and rollback support.
5. Migration Engine: Migration engine is responsible for data location re-computation and distribution in case of addition/ removal of nodes and re-computation of shard keys.  It will make use on of the replicas as a pseudo shard to manage the migration the changing the topology ad per the new migrations.
6. Connection Manager: The Connection Manager is responsible for establishing, maintaining, and monitoring connections between the orchestration system and PostgreSQL nodes. The module manages automatic connection retries, connection pooling, reconnection handling, connection failure detection, and connection health monitoring. It also updates connection states dynamically during topology changes such as failover or node removal.
7. Application access endpoints: The Application Access Endpoint layer acts as the external communication interface for the orchestration system. The system may expose REST APIs, gRPC APIs, or optionally Kafka-based ingestion pipelines to support query ingestion, cluster management operations, orchestration commands, and administrative actions. This module acts as the primary entry point for client applications and external services interacting with the distributed orchestration platform
8. Shard Key Store: The Shard Key Store is a persistent metadata layer used to store shard key definitions and shard routing metadata for distributed tables. The shard key definitions are maintained both in persistent storage and in-memory during runtime to support fast routing decisions. This module plays a critical role in ensuring deterministic shard resolution and efficient query routing.
9. Query handler: The Query Handler is responsible for ingesting incoming SQL queries and extracting essential query metadata such as shard keys, query type, operation type, and query scope. This module uses PostgreSQL-compatible AST parsing libraries to analyze query structure while intentionally avoiding full query rewriting or syntax transformation. The extracted metadata is forwarded to downstream planning and routing modules.
10. Query Router: The Query Router is responsible for determining the execution scope of incoming queries and routing them to the appropriate distributed nodes. Routing decisions are made using shard keys, consistent hashing, shard ownership metadata, and query execution scope. This module forms the core distributed routing layer of the orchestration system and is responsible for minimizing unnecessary cross-node communication whenever possible.
11. Execution  planner: The Execution Planner is responsible for selecting the execution strategy for distributed query execution. The planner uses lightweight rule-based decision logic to determine whether a query should use single-shard execution, scatter-gather execution, collocated join execution, or controlled non-collocated join execution. The planner is intentionally designed as an execution strategy selector rather than a full distributed SQL optimizer or cost-based query planner.
12. Execution Module: The Execution Module contains the internal execution functions responsible for carrying out the distributed execution strategies selected by the planner. The module dispatches queries to the required PostgreSQL nodes, coordinates distributed execution flows, collects intermediate execution states, and manages execution lifecycle coordination. The actual SQL execution and transaction processing remain fully handled by PostgreSQL itself, while this module acts as a distributed execution coordinator.
13. Result aggregation service: The Result Aggregation Service is responsible for aggregating and formatting query results returned from multiple distributed nodes. The service merges partial results into a unified PostgreSQL-like response structure before returning the final response to the client application. This module is especially important for scatter-gather execution and controlled distributed join execution.
14. Repository Module: The Repository Module contains low-level internal database access methods used by the orchestration platform itself. The module is responsible for internal metadata persistence, state manipulation, configuration storage, and orchestration-related data access. The repository layer intentionally contains simple and isolated database interaction logic to maintain separation between orchestration logic and storage access logic.
15. Monitoring service: The Monitoring Service is responsible for continuously monitoring distributed node behavior, read/write traffic, replication lag, node health, execution latency, and emerging access patterns. The module also acts as the observability layer of the platform by generating operational metrics, telemetry, and runtime diagnostics required for orchestration decisions and debugging.
16. Backed Access APIs:  The Backend Access API layer exposes REST and/or gRPC APIs used by frontend dashboards, administrative interfaces, orchestration tools, and external management services. This module acts as the communication bridge between the orchestration backend and external client-facing systems.
17. Caching Service: Caching service will be used to cache important data such as node connection details, database schema and shard keys in memory so they are easily accessible during application runtime.

### Features whose implementation is not finalized:

1. Shard Key Inference : 
    
    The Shard Key Inference module is intended to determine optimal shard keys for distributed tables using heuristic-based or machine-learning-assisted approaches. The shard key generation strategy may operate using static schema analysis, dynamic query access pattern analysis, or a hybrid combination of both approaches. The primary objective of this module is to improve data locality, reduce cross-shard communication, and optimize routing efficiency.
    
    However, the implementation of this module is currently unresolved due to several architectural uncertainties. The system currently lacks a clearly defined mechanism for determining when newly inferred shard keys should be accepted or rejected. Additionally, the impact of shard key changes on existing distributed data placement and migration performance remains undefined. The telemetry and query-analysis requirements necessary to accurately identify un-optimized access patterns are also currently unknown.
    
2. Data Migration Engine for Node Addition and Removal : 
    
    The Data Migration Engine is intended to handle topology changes caused by node addition, node removal, replica redistribution, or shard re-balancing operations. The module is responsible for recomputing shard ownership mappings, migrating distributed data to new nodes, synchronizing live ingestion during migration, and validating consistency between old and new distributed topologies.
    
    The migration engine is expected to support near-live migration with minimal downtime while ensuring that ongoing ingestion and query execution can continue during migration operations. The module must also verify data consistency between migrated and source data before migration finalization.
    
    However, multiple implementation challenges remain unresolved. The interaction between replication topology changes and migration workflows is currently undefined. The system currently lacks a finalized strategy for maintaining strict consistency during simultaneous ingestion and migration without requiring temporary additional nodes for buffering or synchronization. Additionally, the overall system-wide performance impact of large-scale migration operations remains unknown.
    
3. SSupport for Non-Colocated Joins : 
    
    The system intends to support controlled non-colocated joins across distributed shards. Unlike colocated joins, where related data exists on the same shard, non-colocated joins require distributed data fetching and cross-node coordination before the final join operation can be completed.
    
    The current architectural direction includes strategies such as centralized joins, distributed fetch-and-merge execution, and streaming/window-based join execution. These approaches aim to support OLTP-oriented distributed joins while attempting to minimize unnecessary cross-node communication and memory usage.
    
    However, this module remains highly experimental and architecturally unresolved. Large-scale distributed joins may lead to memory explosion due to uncontrolled intermediate result transportation between shards. Network overhead and distributed synchronization costs are also currently undefined. While streaming or sliding-window execution strategies may reduce memory pressure, there is currently no guarantee that independently streamed windows from multiple shards will contain the complete join information required to correctly finalize the distributed join operation. As a result, the system currently assumes that non-colocated joins will remain constrained, bounded, and optimized specifically for OLTP-style workloads rather than large-scale analytical processing.
    

### Missing Architecture Parts:

- Authentication and authorization for users, projects, and node access.
- Backup, restore, and disaster recovery so the system can recover from bad migrations or data loss.
- Rebalancing and cleanup logic after shard movement, replica changes, or node removal.
- Quotas / rate limiting / isolation so one project or shard does not starve the rest.
